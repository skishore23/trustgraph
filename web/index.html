Decide where your agent's output can go, based on what it read.

Your agent may read the salary file and the roadmap. It writes a "Q3 headcount plan" from both and posts it to #engineering. The plan is new, so it has no permissions of its own, and nothing stops it.

TrustGraph is policy-as-code for what agents produce. One small YAML policy says who may read each source and who receives each action. For every output it answers allow, needs approval or deny, with the reason. Restrictions follow the data.

 salaries        roadmap
 hr              hr, engineering
    └───────┬───────┘
            ▼
  Q3 headcount plan
  hr only (the overlap)
            │
    ┌───────┴───────┐
    ▼               ▼
 #hr              #engineering
 ALLOWED          DENIED

    Written by agents, approved by people

    Agents draft the policy: every command has --json output with a stable code, a path and a did-you-mean suggestion, and inline tests say what must be allowed or denied. A person reviews the plain-English explanation and a diff that flags every widening.

    $ trustgraph policy check --json trustgraph.policy.yaml
{
  "diagnostics": [
    {
      "code": "unknown_name",
      "message": "`leadrship` is not a group or person in this policy",
      "path": "sources.comp_review.readers[1]",
      "severity": "error",
      "suggestion": "did you mean `leadership`?"
    }
  ],
  "ok": false
}

    The rule

    readers(output) = readers(input 1) ∩ readers(input 2) ∩ …
allowed         = everyone the action reaches ⊆ readers(output)

    Approval adds a human check; it never widens who may read a source. Anything the policy does not name is denied.

    How we know it works

    Decisions are deterministic: no language model in the decision path, so the same policy and inputs give the same answer. That makes them repeatable, not right; your tests say what right means.

    The simulator above runs the shipped runtime, not a model of it, and checks five invariants after every step. A simulated schedule is evidence, not a proof over every execution.

    Ten bounded Kani proofs cover the allow / needs-approval / deny ordering, the approval window and the reader-set rules, and all pass in CI. They prove those kernels within fixed bounds, not the whole system. Verification details

    Use it

    TrustGraph ships today as a Rust library and a CLI.

    cargo install --locked --git https://github.com/skishore23/trustgraph trustgraph-cli

trustgraph policy init --path trustgraph.policy.yaml
trustgraph policy check trustgraph.policy.yaml
trustgraph policy test trustgraph.policy.yaml
trustgraph policy simulate trustgraph.policy.yaml --seed 0
trustgraph policy explain trustgraph.policy.yaml
trustgraph policy diff old.policy.yaml trustgraph.policy.yaml

    Next: trustgraph serve, a local HTTP and MCP service. It is not built yet.

    Limits

    • It only knows the inputs your system reports.
    • It decides; it does not act. Ask right before acting, and act only on "allow".
    • One sensitive input restricts the whole output.
    • Groups are lists of names in the file, not a directory.

    Where it fits

    Permission databases such as SpiceDB or OpenFGA decide what your agent may read. TrustGraph decides where what it wrote may go.
