Policy-as-code for what AI agents produce

Decide where your agent's output can go — based on what it read.

Permission systems decide what an agent may read. They lose track the moment it writes something new. TrustGraph follows the data: one small YAML policy answers allow, needs approval or deny for every output, and says why.

Try the playground GitHub

Access control stops at the first thing your agent writes.

  1. 1 · Reads

    It reads two files it is allowed to read.

    The HR salary file and the product roadmap. Your permission system checks both. Both pass.

  2. 2 · Writes

    It writes something new.

    A “Q3 headcount plan”. It mixes salaries with the roadmap — and as a new document, it has no permissions of its own.

  3. 3 · Leaks

    It posts the plan to #engineering.

    Nothing checks a summary, so nothing stops it. Everyone in the channel can now read salary data.

Restrictions should follow the data. That is what TrustGraph does.

    How it works

    Two rules do all the work.

    Rule 1

    An output is only as readable as its inputs.

    Only people who may read every source the agent used may read what it wrote.

    readers(output) = readers(a) ∩ readers(b) ∩ …

    Rule 2

    An action is allowed only if everyone it reaches is in that overlap.

    The agent must also be listed on the action and on every source it read.

    audience(action) ⊆ readers(output)

    • Approval never widens. It adds a human check on top. It cannot let anyone read a source they could not read before.
    • Anything not named is denied. Unknown agents, sources, actions and people get “deny”, with the reason.

    How we know it works

    Three kinds of evidence, each with a stated limit.

    Deterministic decisions

    No language model in the decision path. The same policy and the same inputs give the same answer, every time.

    Limit Deterministic is not the same as right: your tests say what right means.

    Simulator on the real runtime

    Seeded runs push the runtime through policy changes, crashes, torn journal writes and approval expiry, checking five safety invariants at every step.

    Limit A simulated schedule is evidence, not a proof over every possible execution.

    Bounded proofs of the core rules

    Kani proof harnesses check the allow / needs-approval / deny ordering, the approval time window and the reader-set rules.

    Limit They cover those kernels within fixed bounds — not group expansion, the journal or the whole system.

    Use it today

    A Rust library and a CLI.

    Install the CLI, write a policy, and run it in CI next to your code. The binary is trustgraph.

    Coming next trustgraph serve — a local service over HTTP and MCP that your agents call before they act.

    # install
cargo install --git https://github.com/skishore23/trustgraph trustgraph-cli

# write, check and test a policy
trustgraph policy init --path trustgraph.policy.yaml
trustgraph policy check trustgraph.policy.yaml
trustgraph policy test trustgraph.policy.yaml

# stress it, then show a human what it says and what changed
trustgraph policy simulate trustgraph.policy.yaml --seed 0
trustgraph policy explain trustgraph.policy.yaml
trustgraph policy diff old.policy.yaml trustgraph.policy.yaml

    What TrustGraph does not do

    • It only knows the inputs your system reports. If an agent reads something and your system does not say so, the policy cannot account for it.
    • Your system must ask for a decision right before it acts, and act only on “allow”.
    • It decides. It does not send, block or approve anything itself.

    Permission databases such as SpiceDB or OpenFGA decide what your agent may read. TrustGraph decides where what it wrote may go. Use both.
